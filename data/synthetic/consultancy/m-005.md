# End-of-Day Batch Best Practices

**Effective date:** 2025-10-01
**Document type:** Guide
**Publisher:** Meridian ETRM Consulting Knowledge Base

## Purpose

This guide sets out generic best practices for designing, sequencing, and monitoring end-of-day (EOD) batch processing in energy and commodity trading risk management (ETRM) and commodity trading and risk management (CTRM) environments. It is a general playbook. It contains no client-specific configuration, and teams should adapt it to their own system landscape and operating model.

## Job Sequencing

EOD batches usually contain dependent steps, and the order of those steps determines whether downstream results can be trusted. The most important rule is that price import must finish before mark-to-market runs. Valuation, exposure, and P&L calculations that run against stale or partial prices produce results that look valid but are wrong. Build the dependency chain explicitly so the scheduler cannot start a valuation job while its price input is still loading.

Good practice includes:

- Map every job's inputs and outputs before scheduling it.
- Make dependencies visible in the scheduler, not only in run books.
- Gate downstream jobs on upstream completion status, not on clock time.
- Avoid overlapping jobs that write to the same tables or positions.

## Ownership and Recovery

Every batch job should have a documented retry procedure and a named owner. The owner is accountable for the job's health, for responding to failures, and for keeping the run book current. A retry procedure should state when a job may be re-run safely, whether it is idempotent, what state must be cleaned up before a re-run, and who must approve a re-run that touches downstream results.

Teams should review ownership and retry documentation whenever a job changes, and after any incident in which the documented procedure proved inadequate.

## Monitoring and Alerting

Do not rely on users to notice a late or failed batch. Alert on batch overruns as well as outright failures. An overrun alert fires when a job or the overall batch exceeds its expected run window, which gives operators time to act before business users are affected. Alerts should route to the job owner and an escalation contact, and should be tested periodically.

Useful monitoring practices include:

- Track start time, end time, and status for every job and for the batch as a whole.
- Set expected run windows based on historical performance, and review them as volumes grow.
- Distinguish between failed, late, and completed-with-warnings states.
- Record every alert and its resolution to support later review.

## Related Practice

Consistent batch design reduces incident frequency and shortens recovery time. Pair this guide with your organisation's change management and incident response procedures.
